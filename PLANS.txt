DECISION: STAY SYNCHRONOUS FOR NOW
-----------------------------------------------------------------------

AnalysisPipeline.md recommends async (sync gate + queued analysis) as the
production pattern. That is correct eventually. Not yet.

Cost of async today:

  - A broker and a worker. Celery/ARQ needs Redis plus a second container,
    added while we are actively simplifying deployment (k8s removal).
  - 'processing' becomes a durable state. Today it is transient -- inserted
    at the top of the request, resolved before commit (meals.py:220). It
    never survives a request. Async forces GET /api/meals, Log.tsx, and the
    upload response to handle "not done yet", plus distinguish pending from
    stuck.
  - The transaction splits. create_meal_with_metadata() is one transaction,
    one commit. Async becomes commit-gate-then-update-later: two
    transactions needing idempotency and retry-safety.
  - Debugging moves out of the request path into worker logs.

Value of sync today: the prompts and schemas do not exist yet and will be
iterated on constantly. Sync gives one loop -- upload, see the full result,
see the traceback if it broke. That iteration speed outweighs 15s of
latency while we are the only user. A user who just took a photo and asked
for analysis tolerates a 20s wait with a progress indicator.

SWITCH TO ASYNC WHEN ONE OF THESE FIRES:

  1. Segmentation ships. A 3rd and 4th model call is where the budget blows.
  2. p95 upload exceeds ~30s.
  3. A gateway timeout is hit. CHECK THIS NOW -- Cloudflare defaults to
     100s, many proxies to 30s or 60s. A hard 30s ceiling overrides
     everything above and forces async early.
  4. Mobile clients arrive. A dropped connection currently discards the
     entire analysis.

Intermediate option if latency bites before we are ready for a queue:
FastAPI BackgroundTasks. Return the gate result immediately, run analysis
in-process after the response. No broker. Does not survive a restart, so
it is not the production answer.

of one. Full rationale in docs/Guide.md -> Database schema and in the
header comments of 0001_baseline.sql.

RESOLVED -- the fail-open gate. evaluate_quality() now returns two gates
with opposite failure preferences:

  accepted        fails OPEN.  "No reason to reject." Unchanged behaviour:
                  an outage must not reject every upload with a message
                  claiming the user's photo is unclear.

  nutrition_ready fails CLOSED. Requires is_food_image is True -- positive
                  evidence, not the absence of a rejection. Blocked reasons:
                  not_food / vision_unavailable / photo_rejected.

  analysis_complete  informational: did BOTH analyzers run? A meal can be
                  nutrition_ready with analysis_complete false (OpenCV died,
                  vision confirmed food) -- discount confidence, do not refuse.

The case this exists for: OpenCV measures blur/brightness/resolution and has
no concept of food, so during a vision outage a sharp photo of a dog passes
the storage gate. Pinned by
test_dog_photo_during_vision_outage_is_accepted_but_blocked.

PHASE 2 CONTRACT: anything emitting a calorie or macro number branches on
nutrition_ready, never on accepted.

RESOLVED at the API layer -- nutrition_ready is now a response field, not a
new status value (a 4th status was considered and rejected: it would be one
more thing every consumer has to branch on, where nutrition_ready is already
the correct branch). Both GET /api/meals and GET /api/meals/{id} return it
directly, sourced from v_meal_list / v_meal_detail rather than a JSONB path.
STILL OPEN on the frontend: no page reads it yet -- there is nothing to show
until Phase 1 produces foods. Belongs in Phase 1 same as before.
