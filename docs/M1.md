# Platter — M1: Visible Foods Build Brief

M1 makes the scan loop visibly useful: an accepted meal photo returns detected
food labels, per-item confidence, and explicit ambiguity. It does **not**
estimate nutrition. M2 remains blocked until M1's food-identification quality
gate passes.

**M1 promise:** upload a usable plate photo and see the foods Platter believes
are visible (for example, “jollof rice, grilled chicken, plantain”), including
how confident it is and what remains ambiguous.

Related documents: [`MVP.md`](MVP.md), [`AnalysisPipeline.md`](AnalysisPipeline.md),
[`Guide.md`](Guide.md), and [`PLANS.txt`](../PLANS.txt).

---

## Definition of done

- Rejected photos do not call the visible-foods model.
- Accepted photos write a `quality_context` artifact and a `visible_foods`
  artifact in the same analysis run as the quality artifacts.
- Every visible-food artifact is projected into `meal_foods`; the artifact
  remains the authoritative, lossless record.
- `GET /api/meals/{meal_id}` returns the latest run's foods only and enforces
  ownership. Scan and Log render labels and confidence without implying
  nutrition.
- A visible-foods failure degrades the run but never loses an already stored
  upload or turns a successful upload into a 500.
- The M1 evaluation gate below passes before M2 begins.

## Critical blockers to resolve now, before coding M1

### 1. Prove the deployed request path exists and establish its deadline

The manifests point to an AWS Application Load Balancer, not a Cloudflare API
proxy (`k8s/ingress.yml`); Cloudflare R2 is storage. The manifest does not set
the ALB idle timeout, so the AWS default is 60 seconds unless the live load
balancer was changed separately. A prior DNS request for `useplatter.ca` also
failed from the development environment, so do not assume production is
reachable.

Before coding, verify all of the following against the live environment:

- DNS for `useplatter.ca` and `api.useplatter.ca`, certificate validity, ALB
  listener rules, target health, and `GET /health`.
- The actual ALB idle timeout and any CDN, API gateway, or client timeout that
  sits in front of it.
- Authenticated upload p50/p95 latency, timeout rate, and response codes for
  the current one-model request through the public endpoint.

**Exit criterion:** the real deadline is recorded, the endpoint is healthy,
and a baseline latency report exists. If current p95 is already close to the
deadline, pause M1 and make an explicit sync/async or capacity decision first.

### 2. Establish whether a second model call is safe at real concurrency

The backend is one replica with the default single Uvicorn worker and a 400m
CPU limit. The `async` upload route invokes synchronous OpenCV, R2, and
Anthropic work directly. A long-running upload can therefore delay unrelated
requests; a second vision call changes availability as well as latency.

Run a small authenticated load test through the deployed endpoint with one,
two, and five concurrent representative uploads. Measure upload latency,
errors/timeouts, health-endpoint latency, CPU/memory, and Anthropic failures.

**Exit criterion:** record an agreed M1 operating envelope: concurrency,
maximum p95 latency, and a remediation trigger. If it fails, choose one before
feature work: more workers/replicas, moving blocking work off the event loop,
or a durable async pipeline. `BackgroundTasks` is only a temporary client-wait
reduction; it does not add capacity or survive a pod restart.

### 3. Freeze the evaluation set before prompt tuning

M1 is the quality gate for M2. Build a hand-labeled, versioned set of roughly
50 real meal photos before changing prompts. Include the cuisines and plate
styles the MVP will demo (including jollof, egusi, plantain preparations and
mixed plates), difficult lighting/occlusion, and non-food negatives. For each
photo, record visible item labels and allowed aliases.

Define the go/no-go thresholds before seeing M1 results: per-item precision,
recall, false positives, and the minimum acceptable result by cuisine. Keep a
small holdout set for prompt-regression checks.

**Exit criterion:** the labeled set, rubric, and thresholds are committed or
stored in an access-controlled evaluation location. M2 cannot start without a
passing report from this fixed set.

### 4. Confirm database deployment state and migration path

The documented development schema was intentionally re-baselined; the old
claim that `0001_baseline.sql` could silently fail to reconcile a live schema
is stale. That does not prove a separate persistent production database has
the same shape.

Inventory every database that M1 could deploy to. For any persistent database,
take a schema-only dump and compare it with the applied migrations, then record
the current `schema_migrations` state. Do not add `0003`+ until the target is
known.

**Exit criterion:** one named migration target, a backup/rollback plan, and a
verified forward-only migration path. M1 itself should need no DDL for foods,
because the existing artifact and `meal_foods` schema already support it.

### 5. Put a minimal cost and abuse boundary around the new model call

Free account creation plus a 15 MB upload limit makes every accepted upload a
potentially expensive model request. Capture current token/latency/cost data
for representative images, set a spend alert/cap, and decide a per-user/IP
upload rate limit before public M1 traffic.

**Exit criterion:** a budget owner, alert threshold, and enforced or
operationally monitored request limit exist before enabling the feature beyond
controlled testers.

## Build scope

### Backend and graph

1. Add `VISIBLE_FOODS_SCHEMA` and a versioned visible-foods prompt in
   `app/graph/schema.py`. The response must carry a display label,
   `possible_types`, `possible_preparations`, and a 0–1 confidence per item.
   It must distinguish uncertainty from a confident guess.
2. Implement `build_quality_context()` as a pure dict-in/dict-out function.
   It distills the quality result into constraints for the food-identification
   prompt, including portion difficulty, depth uncertainty, overlap, and
   relevant technical/vision caveats. Unit-test its mapping separately.
3. Rename/extend graph state to a meal-analysis state. Decode and JPEG-encode
   the source image once; reuse that preprocessed image for both model nodes.
4. Add `visual_understanding_node`, with the same never-raise contract as the
   quality node. Return a structured `analysis_error` payload on missing keys,
   model refusal, malformed output, or network failure.
5. Add conditional routing: quality always runs; only an `accepted` meal runs
   visible-food analysis. A rejected photo must not incur the second call.
6. Bump `PIPELINE_VERSION` when the graph shape changes. Persist the actual
   model and prompt versions with the new artifact.

### Persistence and API

1. Create one analysis run for the whole upload pipeline and persist
   `technical_quality`, `vision_quality`, `quality_context`, and
   `visible_foods` artifacts with status, error code, provenance, and latency.
2. Project `visible_foods` into `meal_foods` using the run ID and stable
   ordinal. Never make `meal_foods` a competing write source.
3. On a degraded visible-food stage, persist the error artifact, mark the run
   degraded, and return the stored meal with an empty foods list. Do not alter
   the quality verdict or `nutrition_ready` semantics.
4. Keep read behavior on `v_meal_detail` / `v_meal_foods`: return foods from
   the latest coherent run only. Add route tests for successful foods,
   rejected photos, degraded foods, and cross-user access.

### Frontend

1. In Scan, show detected foods only after a completed accepted meal has food
   output. Display confidence in plain language and preserve ambiguity; do not
   show a calorie/macro placeholder.
2. In Log, show concise food labels from the detail/list contract without
   adding a JSONB-reading client-side workaround.
3. Give a graceful neutral state for “analysis completed but food labels are
   unavailable.” Never claim that an empty list means no food was present.
4. Keep nutrition UI gated on `nutrition_ready`; M1 does not relax that rule.

## Checks to perform during M1

| Area | Check during implementation | Evidence required before merge |
|---|---|---|
| Routing | Rejected, non-food, and retake photos skip the second VLM call; accepted meals call it once. | Unit test spies/counters plus graph routing tests. |
| Image handling | Both vision stages reuse one normalized JPEG; HEIC and corrupt inputs retain current behavior. | Tests for JPEG/PNG/HEIC and decode failure. |
| Schema validity | The model schema rejects incomplete/invalid items; model refusal and malformed responses degrade safely. | Node tests for valid output, refusal, malformed JSON, and exception paths. |
| Quality context | Context reflects known quality limitations and never invents a positive food signal. | Table-driven pure-function tests from representative gate payloads. |
| Persistence | Artifact statuses, latency, model/prompt version, run status, and food projection remain coherent. | DB tests for success, degraded stage, and a new analysis run. |
| Latest-run reads | A re-analysis cannot combine foods from one run with a gate verdict from another. | View/repository test with two runs for the same meal. |
| API security | Detail responses contain only the authenticated user's meal and foods. | Ownership/404 route tests. |
| UI honesty | Low confidence and ambiguous types are legible; unavailable analysis is not described as an empty plate. | Component/manual acceptance checklist. |
| Latency and cost | Stage latency is stored and dashboard/queryable; model token/cost samples are recorded. | Staging report and alert/dashboard link or operating note. |
| Operational failure | Anthropic/R2/db failure leaves no corrupt lifecycle or misleading completion state. | Failure-injection tests and a staging runbook exercise. |

## M1 acceptance and release gates

### Automated gates

- Existing quality-decision regression suite remains green.
- New unit tests cover schema handling, `build_quality_context`, conditional
  routing, and visible-food error behavior.
- DB-backed tests cover artifact persistence, `meal_foods` projection, latest
  run selection, and ownership.
- Frontend build and affected component tests pass.

### Product-quality gate (blocks M2)

Run the frozen evaluation set without changing the prompt. Report:

- Per-item precision and recall, overall and by cuisine/plate style.
- False positives on non-food images and difficult photos.
- Confidence calibration: low-confidence results should actually be less
  reliable than high-confidence results.
- Examples of all failures, grouped into prompt/schema, image-quality,
  taxonomy, and inherently ambiguous categories.

If the predefined food-ID thresholds fail, improve the visual prompt/schema or
the label taxonomy before building nutrition. Do not use nutrition ranges to
mask bad food labels.

### Operational release gate

Repeat the public-path concurrency test with M1 enabled. Confirm p95, error
rate, timeout rate, pod health, and cost stay within the operating envelope
chosen before M1. If not, stop the rollout and apply the previously chosen
capacity or async remediation.

---

## Explicit non-goals for M1

- Nutrition, USDA lookup, portion sizing, or calorie/macro display.
- Segmentation, masks, bounding boxes, or portion-correction UI.
- User food-confirmation flows or a manual correction taxonomy.
- Discover, recipes, saves, profile changes, and vibe queries.
- Changing the semantics of `accepted`, `nutrition_ready`, or
  `analysis_complete`.

---

## Suggested implementation sequence

1. Complete the five pre-build gates and record their evidence.
2. Implement schema, quality context, graph state, and routing with unit tests.
3. Persist artifacts and the `meal_foods` projection; add DB/read-model tests.
4. Expose and render foods in Scan and Log with honest empty/degraded states.
5. Run the fixed evaluation set and public-path load test.
6. Release M1 only if the product-quality and operational gates pass; otherwise
   iterate on M1 rather than starting M2.
