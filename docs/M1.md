# Platter — M1: Visible Foods Build Brief

M1 makes the scan loop visibly useful: an accepted meal photo returns detected
food labels, per-item confidence, and explicit ambiguity. It does **not**
estimate nutrition. M2 remains blocked until M1's food-identification quality
gate passes.

**M1 promise:** upload a usable plate photo and see the foods Platter believes
are visible (for example, “jollof rice, grilled chicken, plantain”), including
how confident it is and what remains ambiguous.

Related documents: [`MVP.md`](MVP.md), [`AnalysisPipeline.md`](AnalysisPipeline.md),
[`Guide.md`](Guide.md), and [`PLANS.txt`](../PLANS.txt).

---

## Definition of done

- Rejected photos do not call the visible-foods model.
- Accepted photos write a `quality_context` artifact and a `visible_foods`
  artifact in the same analysis run as the quality artifacts.
- Every visible-food artifact is projected into `meal_foods`; the artifact
  remains the authoritative, lossless record.
- `GET /api/meals/{meal_id}` returns the latest run's foods only and enforces
  ownership. Scan and Log render labels and confidence without implying
  nutrition.
- A visible-foods failure degrades the run but never loses an already stored
  upload or turns a successful upload into a 500.
- The M1 evaluation gate below passes before M2 begins.

## Technical decisions

These are the implementation decisions for M1. They resolve the choices that
the broader pipeline design leaves open for later milestones.

### 1. Execution and scope

- Run M1 synchronously for private MVP development. The upload response is not
  returned until its quality and visible-foods stages have completed. The
  operating evidence and mandatory switch triggers for a durable asynchronous
  pipeline are recorded in [`LOOK_INTO.md`](LOOK_INTO.md).
- M1 is a semantic, visible-food stage only. It must not infer hidden
  ingredients, portions, nutrition, spatial regions, masks, or bounding boxes.
  A sauce obscuring a food is an uncertainty, not evidence of a guessed food.
- Keep the current quality gate as the only routing gate. A decision with
  `accepted == true` runs food identification, including fail-open quality
  outcomes; `accepted == false` never calls the visible-foods model.

### 2. Visible-food contract and taxonomy

The authoritative `visible_foods` artifact has this versioned shape:

```json
{
  "result": "identified",
  "visible_foods": [
    {
      "label": "rice",
      "possible_types": ["jollof rice", "fried rice"],
      "possible_preparations": [],
      "confidence": 0.78
    }
  ],
  "uncertainties": ["the rice is partly covered by chicken"]
}
```

- `result` is either `identified` or `unavailable`. `identified` requires at
  least one food; `unavailable` requires an empty `visible_foods` list and at
  least one concise explanation in `uncertainties`. Model or transport failure
  is an error artifact, not an `unavailable` success result.
- An item has exactly the four fields above. `label` is a lowercase, singular,
  coarse canonical food category (for example `rice`, `chicken`, `plantain`).
  It is the value stored in `meal_foods` and is never a preparation or a
  confident guess at a subtype. Specific dish/type hypotheses belong in
  `possible_types`; cooking methods belong in `possible_preparations`.
- The taxonomy is prompt- and rubric-controlled rather than a closed database
  enum in M1: unfamiliar valid foods must remain expressible. Maintain a
  versioned allowed-alias rubric with the frozen evaluation set; normalize known
  aliases to the chosen canonical label before projection. Add a closed enum
  only when real outputs show that the rubric is insufficient.
- Emit one item per visible food category, merging repeated portions of the
  same category. Return at most 12 items, four type alternatives and four
  preparation alternatives per item, and eight global uncertainties. All text
  must be short, user-readable, and deduplicated.
- Confidence is a finite 0--1 model score, not a claim of measured
  probability. Persist the raw score. The client maps it consistently to
  `high` (>= 0.80), `medium` (>= 0.50 and < 0.80), or `low` (< 0.50), and says
  "Platter's confidence" rather than implying certainty.

### 3. Model, prompt, and image inputs

- Use the existing `claude-opus-4-8` client for both private-MVP vision calls.
  It prioritizes accuracy and avoids introducing a second provider or model
  comparison before the evaluation set exists. Reconsider a lower-cost tier
  only after the frozen evaluation report and representative cost samples.
- Use Anthropic JSON Schema structured output with a new
  `VISIBLE_FOODS_SCHEMA`, `additionalProperties: false`, and a separately
  versioned visible-food prompt. The schema enforces the contract above,
  bounds all arrays, and rejects non-finite or out-of-range confidence values.
- The prompt identifies only what is visibly supported by the image. It asks
  for coarse labels first, alternatives only where genuine ambiguity exists,
  and uncertainty instead of a forced answer. It includes the distilled
  quality context as constraints, never as evidence that a food is present.
- Decode and normalize the upload to one RGB JPEG (maximum edge 1568 px,
  JPEG quality 85) once per analysis. Keep that base64 JPEG in graph state and
  reuse it for both VLM calls. Preserve existing HEIC and corrupt-input
  behavior; a decode failure yields the current error path and no model calls.

### 4. Graph, quality context, and failure behavior

- Rename the state to `MealAnalysisState`. The upload orchestration obtains
  `technical_quality`; the graph receives it with the normalized image, runs
  `image_quality`, evaluates the existing `QualityDecision`, conditionally
  builds context, then runs `visual_understanding`.
- `build_quality_context()` is a separately tested pure function. Include:
  `plate_visible`, `cropped_food`, `bad_angle`, `depth_unclear`,
  `food_overlap_level`, `sauce_hiding_food`, `portion_difficulty`,
  `recommended_action`, and only technical checks that actually tripped.
  Exclude `is_food_image` and `food_confidence`: routing has already consumed
  the former and the latter adds no useful constraint after acceptance.
- The visible-food node makes no automatic retry in the synchronous request;
  retrying doubles a costly, latency-sensitive operation with no evidence that
  the second answer is better. It never raises. Map refusal, malformed or
  schema-invalid output, missing required content, and upstream/client errors
  to stable error codes (`model_refusal`, `invalid_response`,
  `upstream_error`, or `client_error`) without exposing raw provider details to
  an API client.
- Persist `technical_quality` and `vision_quality` for every run. For an
  accepted meal, persist an `ok` `quality_context` artifact and an `ok` or
  `error` `visible_foods` artifact. For a rejected meal, persist a `skipped`
  `visible_foods` artifact with reason `photo_rejected`; do not create a
  quality-context artifact. A visible-food error makes the run `degraded` but
  does not change the gate verdict, upload lifecycle, or nutrition semantics.
- Project only an `identified` result into `meal_foods`, with stable list
  ordinal. The artifact is the lossless source of truth; `meal_foods` remains
  replaceable derived data. A new analysis always creates a complete new run,
  and views expose foods only from that run.

### 5. API, UI, evaluation, and release

- Extend `GET /api/meals/{meal_id}` with full `foods` and a derived
  `food_analysis_status`: `available`, `unavailable`, or `not_applicable`.
  It is derived from the latest run's visible-food artifact, not inferred from
  an empty `foods` array. Extend `GET /api/meals` with the same status plus a
  concise derived `food_labels` array for Log; do not issue one detail request
  per log card. Both fields come from the latest-run views/projection, never
  from client-side JSONB parsing. Preserve ownership and the existing 404
  behavior. The synchronous upload response stays small; Scan fetches this
  detail once its upload succeeds rather than duplicating a second food
  representation in `POST /api/upload`.
- Scan renders the canonical label, confidence band, and alternatives as
  hypotheses (for example, "Rice -- possibly jollof or fried rice"). Log uses
  the same detail/read-model contract. `unavailable` renders a neutral
  explanation; it never means "no food was present." `not_applicable` follows
  the rejected-photo UI. No M1 surface shows calories, macros, portions, or a
  nutrition placeholder.
- Create and freeze a roughly 50-photo, access-controlled, versioned
  evaluation set before prompt tuning is finalized or M2 begins. It includes
  representative cuisines/plate styles (including jollof, egusi, plantain
  preparations, mixed plates), difficult quality cases, and non-food images;
  each record has canonical labels and allowed aliases.
- Before evaluating, commit these thresholds in the evaluation rubric:
  micro-averaged per-item precision >= 0.85 and recall >= 0.75; for every
  represented priority cuisine or plate-style cohort with at least ten labeled
  items, precision >= 0.75 and recall >= 0.60; zero `identified` results on
  non-food negatives; and measured precision >= 0.85 for items in the high
  confidence band, with high-band precision no lower than medium-band
  precision. M2 remains blocked until that frozen rubric passes.

## Preconditions and release gates

The current MVP priority is feature speed. Production-path verification and
database readiness are treated as satisfied by the team. Capacity/concurrency
and cost/abuse controls are deferred from implementation, but remain required
before a public rollout. The evaluation set remains an M2 gate, not training
data or a prerequisite to build the M1 feature.

### 1. Prove the deployed request path exists and establish its deadline

The manifests point to an AWS Application Load Balancer, not a Cloudflare API
proxy (`k8s/ingress.yml`); Cloudflare R2 is storage. The manifest does not set
the ALB idle timeout, so the AWS default is 60 seconds unless the live load
balancer was changed separately. A prior DNS request for `useplatter.ca` also
failed from the development environment, so do not assume production is
reachable.

Before coding, verify all of the following against the live environment:

- DNS for `useplatter.ca` and `api.useplatter.ca`, certificate validity, ALB
  listener rules, target health, and `GET /health`.
- The actual ALB idle timeout and any CDN, API gateway, or client timeout that
  sits in front of it.
- Authenticated upload p50/p95 latency, timeout rate, and response codes for
  the current one-model request through the public endpoint.

**Exit criterion:** the real deadline is recorded, the endpoint is healthy,
and a baseline latency report exists. If current p95 is already close to the
deadline, pause M1 and make an explicit sync/async or capacity decision first.

### 2. Establish whether a second model call is safe at real concurrency (deferred)

The backend is one replica with the default single Uvicorn worker and a 400m
CPU limit. The `async` upload route invokes synchronous OpenCV, R2, and
Anthropic work directly. A long-running upload can therefore delay unrelated
requests; a second vision call changes availability as well as latency.

Run a small authenticated load test through the deployed endpoint with one,
two, and five concurrent representative uploads. Measure upload latency,
errors/timeouts, health-endpoint latency, CPU/memory, and Anthropic failures.

**Deferred decision:** do not block M1 implementation on this while the product
is in private MVP development. Before public rollout, record an agreed M1
operating envelope: concurrency,
maximum p95 latency, and a remediation trigger. If it fails, choose one before
feature work: more workers/replicas, moving blocking work off the event loop,
or a durable async pipeline. `BackgroundTasks` is only a temporary client-wait
reduction; it does not add capacity or survive a pod restart.

### 3. Freeze the evaluation set before prompt tuning (M2 gate)

M1 is the quality gate for M2. Build a hand-labeled, versioned set of roughly
50 real meal photos before changing prompts. Include the cuisines and plate
styles the MVP will demo (including jollof, egusi, plantain preparations and
mixed plates), difficult lighting/occlusion, and non-food negatives. For each
photo, record visible item labels and allowed aliases.

Define the go/no-go thresholds before seeing M1 results: per-item precision,
recall, false positives, and the minimum acceptable result by cuisine. Keep a
small holdout set for prompt-regression checks.

This is an evaluation set, not model training data: the application continues
to use the vision model as-is. The labels let us measure its outputs and catch
regressions. It can be assembled after M1 works end-to-end, but before prompt
tuning is finalized or M2 begins.

**Exit criterion:** the labeled set, rubric, and thresholds are committed or
stored in an access-controlled evaluation location. M2 cannot start without a
passing report from this fixed set.

### 4. Confirm database deployment state and migration path

The documented development schema was intentionally re-baselined; the old
claim that `0001_baseline.sql` could silently fail to reconcile a live schema
is stale. That does not prove a separate persistent production database has
the same shape.

Inventory every database that M1 could deploy to. For any persistent database,
take a schema-only dump and compare it with the applied migrations, then record
the current `schema_migrations` state. Do not add `0003`+ until the target is
known.

**Exit criterion:** one named migration target, a backup/rollback plan, and a
verified forward-only migration path. M1 itself should need no DDL for foods,
because the existing artifact and `meal_foods` schema already support it.

### 5. Put a minimal cost and abuse boundary around the new model call (deferred)

Free account creation plus a 15 MB upload limit makes every accepted upload a
potentially expensive model request. Capture current token/latency/cost data
for representative images, set a spend alert/cap, and decide a per-user/IP
upload rate limit before public M1 traffic.

Track this in `docs/LOOK_INTO.md` during private MVP development. A budget
owner, alert threshold, and enforced or operationally monitored request limit
must exist before enabling the feature beyond controlled testers.

## Build scope

### Ordered implementation actions

1. **Define the contract.** Add `VISIBLE_FOODS_SCHEMA`, the versioned visible
   prompt, the taxonomy/alias normalizer, and unit tests for valid identified
   and unavailable results plus every invalid boundary. Record the taxonomy
   version or hash as the artifact `config_hash`.
2. **Refactor the analysis invocation.** Replace the quality-only state and
   runner with `MealAnalysisState` / a meal-analysis runner that normalizes one
   JPEG, carries `technical_quality`, evaluates the current gate, and routes
   accepted versus rejected inputs exactly as specified above. Test that the
   visible model is called once only for accepted inputs and that both VLM
   stages receive the same image bytes.
3. **Build context and the node.** Implement and table-test the pure
   `build_quality_context()`, then add `visual_understanding_node` with
   structured-output validation, provenance, latency timing, sanitized stable
   error codes, and the never-raise contract.
4. **Persist one coherent run.** Extend upload orchestration to write the two
   quality artifacts, accepted-only context, and visible-food `ok`, `error`,
   or `skipped` artifact in one run; project `identified` foods through
   `replace_foods`; finish the run as succeeded or degraded. Test success,
   rejection, unavailable success, visible-node failure, corrupt input, and
   a subsequent reanalysis run.
5. **Expose read models.** Add a forward-only migration that updates the
   latest-run views with `food_analysis_status` and list `food_labels`, then
   extend the typed repositories/Pydantic contracts and ownership route tests.
   Do not create a new foods table or expose artifacts/JSONB directly.
6. **Render the product.** Add one authenticated meal-detail fetch after a
   successful Scan upload; render labels, confidence bands, alternatives, and
   unavailable/rejected states. Render list labels from `GET /api/meals` in
   Log. Remove or retain no nutrition placeholders only where they remain
   clearly future-facing; do not render any nutrition value.
7. **Prove the release gates.** Run the automated suites, then create/freeze
   the evaluation set and rubric, measure the stated thresholds, and collect
   the private-to-public operating evidence in `LOOK_INTO.md`. M2 starts only
   after the quality rubric passes; public rollout waits for the operating
   envelope.

### Backend and graph

1. Add `VISIBLE_FOODS_SCHEMA` and a versioned visible-foods prompt in
   `app/graph/schema.py`. The response must carry a display label,
   `possible_types`, `possible_preparations`, and a 0–1 confidence per item.
   It must distinguish uncertainty from a confident guess.
2. Implement `build_quality_context()` as a pure dict-in/dict-out function.
   It distills the quality result into constraints for the food-identification
   prompt, including portion difficulty, depth uncertainty, overlap, and
   relevant technical/vision caveats. Unit-test its mapping separately.
3. Rename/extend graph state to a meal-analysis state. Decode and JPEG-encode
   the source image once; reuse that preprocessed image for both model nodes.
4. Add `visual_understanding_node`, with the same never-raise contract as the
   quality node. Return a structured `analysis_error` payload on missing keys,
   model refusal, malformed output, or network failure.
5. Add conditional routing: quality always runs; only an `accepted` meal runs
   visible-food analysis. A rejected photo must not incur the second call.
6. Bump `PIPELINE_VERSION` when the graph shape changes. Persist the actual
   model and prompt versions with the new artifact.

### Persistence and API

1. Create one analysis run for the whole upload pipeline and persist
   `technical_quality`, `vision_quality`, `quality_context`, and
   `visible_foods` artifacts with status, error code, provenance, and latency.
2. Project `visible_foods` into `meal_foods` using the run ID and stable
   ordinal. Never make `meal_foods` a competing write source.
3. On a degraded visible-food stage, persist the error artifact, mark the run
   degraded, and return the stored meal with an empty foods list. Do not alter
   the quality verdict or `nutrition_ready` semantics.
4. Keep read behavior on `v_meal_detail` / `v_meal_foods`: return foods from
   the latest coherent run only. Add route tests for successful foods,
   rejected photos, degraded foods, and cross-user access.

### Frontend

1. In Scan, show detected foods only after a completed accepted meal has food
   output. Display confidence in plain language and preserve ambiguity; do not
   show a calorie/macro placeholder.
2. In Log, show concise food labels from the detail/list contract without
   adding a JSONB-reading client-side workaround.
3. Give a graceful neutral state for “analysis completed but food labels are
   unavailable.” Never claim that an empty list means no food was present.
4. Keep nutrition UI gated on `nutrition_ready`; M1 does not relax that rule.

## M1 acceptance and release gates

### Automated gates

- Existing quality-decision regression suite remains green.
- New unit tests cover schema handling, `build_quality_context`, conditional
  routing, and visible-food error behavior.
- DB-backed tests cover artifact persistence, `meal_foods` projection, latest
  run selection, and ownership.
- Frontend build and affected component tests pass.

### Product-quality gate (blocks M2)

Run the frozen evaluation set without changing the prompt. Report:

- Per-item precision and recall, overall and by cuisine/plate style.
- False positives on non-food images and difficult photos.
- Confidence calibration: low-confidence results should actually be less
  reliable than high-confidence results.
- Examples of all failures, grouped into prompt/schema, image-quality,
  taxonomy, and inherently ambiguous categories.

If the predefined food-ID thresholds fail, improve the visual prompt/schema or
the label taxonomy before building nutrition. Do not use nutrition ranges to
mask bad food labels.

### Operational release gate

Repeat the public-path concurrency test with M1 enabled. Confirm p95, error
rate, timeout rate, pod health, and cost stay within the operating envelope
chosen before M1. If not, stop the rollout and apply the previously chosen
capacity or async remediation.

---

## Explicit non-goals for M1

- Nutrition, USDA lookup, portion sizing, or calorie/macro display.
- Segmentation, masks, bounding boxes, or portion-correction UI.
- User food-confirmation flows or a manual correction taxonomy.
- Discover, recipes, saves, profile changes, and vibe queries.
- Changing the semantics of `accepted`, `nutrition_ready`, or
  `analysis_complete`.

---

## Suggested implementation sequence

1. Confirm the production-path and database prerequisites; defer capacity and
   cost controls during private MVP development.
2. Implement schema, quality context, graph state, and routing with unit tests.
3. Persist artifacts and the `meal_foods` projection; add DB/read-model tests.
4. Expose and render foods in Scan and Log with honest empty/degraded states.
5. Run the fixed evaluation set and public-path load test.
6. Release M1 only if the product-quality and operational gates pass; otherwise
   iterate on M1 rather than starting M2.
